## Rehearsal Summary
Scenario used

มีผู้พบโทรศัพท์มือถือพร้อมบัตรนักศึกษานำมาส่งให้เจ้าหน้าที่ศูนย์รับของหาย ต่อมามีบุคคลมาติดต่อขอรับโทรศัพท์คืน แต่ข้อมูลที่ให้ตรงกับสิ่งของเพียงบางส่วน

เจ้าหน้าที่ต้องตรวจสอบว่า บุคคลดังกล่าวเป็นเจ้าของจริงหรือไม่ ควรขอหลักฐานอะไรเพิ่มเติม ข้อมูลใดของสิ่งของสามารถเปิดเผยต่อสาธารณะได้ และควรดำเนินการอย่างไรหากยังไม่สามารถยืนยันเจ้าของได้

นอกจากนี้ ทีมได้จำลองกรณีที่ไม่มีผู้มาติดต่อรับสิ่งของภายในระยะเวลาที่กำหนด เพื่อทดสอบคำถามเกี่ยวกับการจัดเก็บและการจัดการของตกค้าง

ทีมยังจำลองเหตุการณ์ของนักศึกษาผู้พบของที่ไม่แน่ใจว่าควรนำสิ่งของไปส่งที่ใด และเหตุการณ์ของนักศึกษาที่ทำของหายซึ่งต้องค้นหาจากหลายช่องทาง เพื่อทดสอบ Q-07 และ Q-08 เกี่ยวกับพฤติกรรมจริง อุปสรรค และความกังวลของผู้ใช้งาน

- Questions tested:
    - Q-01 ปัจจุบันเมื่อมีคนนำของที่เก็บได้มาส่ง หรือมีคนมาติดต่อขอรับของคืน มีขั้นตอนดำเนินการอย่างไรตั้งแต่ต้นจนจบ?
    - Q-02 จากขั้นตอนที่เล่ามา จุดไหนที่คิดว่าใช้เวลามากที่สุด หรือทำให้เกิดข้อผิดพลาดบ่อยที่สุดในการทำงานปัจจุบัน?
    - Q-03 กรณีที่เป็นของมีค่า (เช่น โทรศัพท์, กระเป๋าสตางค์) มีวิธียืนยันตัวตนผู้มารับอย่างไรให้มั่นใจว่าไม่ใช่มิจฉาชีพ? ขอตัวอย่างเหตุการณ์จริงที่เคยเจอได้ไหมครับ?
    - Q-04 หากมีของตกค้างที่ไม่มีคนมารับเกินระยะเวลาที่กำหนด ปัจจุบันมหาวิทยาลัยมีกฎหรือแนวทางในการจัดการของเหล่านั้นอย่างไร?
    - Q-05 มีของประเภทใดบ้างที่มีกฎชัดเจนว่า "ผู้พบต้องนำมาส่งให้เจ้าหน้าที่ทันที" ห้ามผู้พบโพสต์หาเจ้าของและเก็บไว้เอง?
    - Q-06 ในมุมมองของการจัดการข้อมูล ข้อมูลใดของสิ่งของหรือภาพถ่ายที่ไม่ควรแสดงสู่สาธารณะ? ปัจจุบันมีนโยบายหรือวิธีจัดการเรื่องนี้อย่างไร?
    - Q-07 ขอให้เล่าเหตุการณ์ล่าสุดที่คุณบังเอิญเจอของคนอื่นตกอยู่ คุณจัดการกับของชิ้นนั้นอย่างไร? อะไรคือสาเหตุหลักที่ทำให้คุณตัดสินใจนำหรือไม่นำของไปฝากที่จุดรับฝาก?
    - Q-08 ตอนที่คุณทำของหายครั้งล่าสุด คุณมีวิธีตามหาอย่างไร? สิ่งที่คุณกังวลที่สุดระหว่างที่ยังหาของไม่เจอคืออะไร?
    - Q-09 ในกรณีที่ผู้ทำของหายไม่สามารถเดินทางมาติดต่อขอรับสิ่งของคืนด้วยตนเองได้ ปัจจุบันมีหลักเกณฑ์หรือแนวปฏิบัติอย่างไรในการตรวจสอบเอกสาร/การมอบอำนาจ เพื่อป้องกันการแอบอ้างสวมรอยรับของแทน?
    - Q-10 "จากที่เราได้พูดคุยกันมาทั้งหมด ทีมงานขออนุญาตสรุปเพื่อทวนความเข้าใจนะครับ ว่าปัจจุบันปัญหาหลักคือ [สรุปปัญหา 1-2 ประโยค] และกระบวนการทำงานหลักคือ [สรุปโฟลว์ 1-2 ประโยค]... ตรงนี้มีจุดไหนที่ทางเราเข้าใจคลาดเคลื่อน หรือมีข้อเสนอแนะ/ข้อควรระวังเพิ่มเติมที่ยังไม่ได้กล่าวถึงในวันนี้อีกไหมครับ?"
- Questions that were unclear / leading:

    - Q-03: คำถามเดิมกว้างเกินไป ทำให้ได้เพียงรายการหลักฐาน แต่ไม่ทราบเกณฑ์ตัดสินใจหรือกรณีหลักฐานไม่เพียงพอ
    - Q-04: คำว่า “เกินระยะเวลาที่กำหนด” สมมติว่ามหาวิทยาลัยมีระยะเวลาจัดเก็บอย่างเป็นทางการแล้ว
    - Q-05: ข้อความ “ห้ามโพสต์และเก็บไว้เอง” เป็นคำถามชี้นำ เพราะกำหนดล่วงหน้าว่ามีกฎดังกล่าวอยู่จริง
    - Q-06: การถามว่า “ระบบควรปิดบังข้อมูลใดบ้าง” ซึ่งเน้นการออกแบบระบบมากกว่าการค้นหานโยบายและแนวปฏิบัติในปัจจุบัน
    - Q-07: การถามว่าผู้ใช้จะนำของไปส่งหรือไม่หากมีแอป ซึ่งเป็นการถามพฤติกรรมในอนาคตและชี้นำให้ตอบเชิงบวก
    - Q-08: เมื่อผู้ตอบเสนอช่องทางแจ้งเตือน ทีมอาจรีบนำไปเป็น Requirement โดยยังไม่ได้ค้นหาปัญหาต้นเหตุ
    - Q-10: การถามว่า “ที่สรุปมาถูกต้องใช่ไหม” ซึ่งอาจทำให้ผู้ตอบเห็นด้วยโดยไม่ได้ตรวจสอบรายละเอียด ทีมจึงปรับให้ถามว่าส่วนใดคลาดเคลื่อนหรือควรเพิ่มเติม

- Changes made to the interview guide:
    - Q-03: เพิ่มคำถามเกี่ยวกับเกณฑ์ยืนยันความเป็นเจ้าของ และขั้นตอนเมื่อหลักฐานไม่เพียงพอ
    - Q-04: ปรับคำถามให้ตรวจสอบก่อนว่ามีระยะเวลาจัดเก็บอย่างเป็นทางการหรือไม่
    - Q-05: ตัดข้อความชี้นำเรื่อง “ห้ามโพสต์และเก็บไว้เอง” และเปลี่ยนเป็นคำถามปลายเปิด
    - Q-06: ปรับให้ถามนโยบาย ข้อมูลที่เปิดเผยได้ และข้อมูลที่ต้องปกปิด แทนการเสนอวิธีออกแบบระบบ
    - Q-07: เปลี่ยนจากการถามพฤติกรรมในอนาคต เป็นการถามเหตุการณ์และพฤติกรรมจริงในอดีต
    - Q-08: เพิ่มคำถามติดตามเพื่อค้นหาปัญหาต้นเหตุ ก่อนนำข้อเสนอของผู้ใช้ไปพิจารณาเป็น Requirement
    - Q-09: เพิ่มคำถามตรวจสอบเงื่อนไขการมอบอำนาจและการขอรับของแทนเพื่อป้องกันการสวมรอย
    - Q-10: ปรับคำถามสรุปให้เปิดโอกาสให้ Stakeholder แก้ไขหรือเพิ่มเติมข้อมูล โดยไม่ชี้นำให้ตอบเห็นด้วย
- Evidence rules to use in Week 04:
    - กำหนดรหัสหลักฐานตามบทบาท เช่น E-STAFF-01, E-FINDER-01, E-OWNER-01, E-IT-01 และ E-MANAGER-01
    - หลักฐานทุกชิ้นต้องระบุ Stakeholder Role, Question ID, วันที่, สถานการณ์ และผู้บันทึก
    - จัดประเภทข้อมูลเป็น Fact, Opinion, Preference, Assumption หรือ Proposed Solution
    - แยกคำพูดของ Stakeholder ออกจากการตีความของทีมให้ชัดเจน
    - ไม่แปลงคำตอบเป็น Requirement ทันที แต่บันทึกเป็น Evidence และวิเคราะห์เป็น Candidate Requirement ภายหลัง
    - Candidate Requirement ทุกข้อควรเชื่อมกลับไปยัง Evidence ID และ Question ID ที่สนับสนุน
    - ไม่บันทึกชื่อจริง รหัสนักศึกษา เบอร์โทรศัพท์ หรือข้อมูลส่วนบุคคลของผู้ให้ข้อมูล
    - ข้อเสนอเกี่ยวกับฟีเจอร์หรือเทคโนโลยีต้องบันทึกเป็น Proposed Solution ไม่ใช่ Requirement ที่ยืนยันแล้ว
    - ใช้คำถาม Validation ตอนท้าย เพื่อให้ Stakeholder ตรวจสอบ แก้ไข หรือเพิ่มเติมข้อมูลก่อนจบการสัมภาษณ์
